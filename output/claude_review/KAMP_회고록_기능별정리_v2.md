# KAMP 사출성형 품질 예측 프로젝트 회고 — 구현 기능별 정리

> 대상: K-인공지능 제조데이터 분석 경진대회(KAMP) CN7·RG3 사출성형 과제
> 기간: 2026-09-10(준비가이드) ~ 2026-10-05(운영 파이프라인 검증) · 제출 마감 2026-10-08
> 작성 기준: 준비가이드, 데이터셋, 모델 이론·검증 전략서(9/23), 분석진행 정리(9/30), 확장 아이디어 메모(10/1), 아키텍처 그림 1~5, RF 실험 흐름도, TODO 메모, 10/5 팀장 검토·Codex 교차검수 산출물
> 각 기능은 "배경 → 한 일 → 결과 → 회고(잘된 점 / 어려웠던 점 / 배운 점)" 순서로 적었다. 날짜는 해당 기능을 주로 다룬 시기다.

## 1. 대회 이해와 문제 정의 (9/10 ~ 9/23)

**배경.** 처음에는 "불량을 잘 맞히는 모델"을 만드는 대회라고 생각했다. 그런데 준비가이드를 읽어 보니 이 대회는 리더보드 점수 경쟁이 아니라 창의성, 현장 적용 가능성, 파급효과를 함께 보는 서면·발표 평가였다. 설명 가능성(XAI), 경량성, 확장성도 평가 관점으로 언급되어 있었다.

**한 일.** 그래서 문제를 "불량 확률을 정확히 맞히는 것"에서 "현장에서 검사 우선순위를 정하고, 쌓이는 정답으로 계속 나아지는 구조를 만드는 것"으로 다시 정의했다. 평가 지표도 F1을 기준으로 삼되, F1이 정확도와 다르고 TN이 계산에 들어가지 않는다는 점, 정밀도와 재현율이 현장에서 각각 "불필요한 검사"와 "놓친 불량"이라는 서로 다른 비용을 뜻한다는 점을 따로 정리했다(F1 Score 이해와 활용 자료).

**결과.** 이후 모든 의사결정에서 "점수가 몇 점인가"보다 "이 결과를 현장에서 어떻게 쓰는가"를 같이 묻게 되었다. 이 관점이 뒤에서 CN7은 검사 예산 방식, RG3는 분포 감시 방식으로 운영 방식을 나누는 근거가 되었다.

**회고.**
- 잘된 점: 초반에 평가 기준을 제대로 읽은 덕분에 점수만 쫓는 실험에 시간을 쓰지 않았다.
- 어려웠던 점: 불량이 42행뿐인 데이터에서 F1 하나로 모델 우열을 말하기 어렵다는 걸 처음에는 체감하지 못했다. 불량 한 건 차이로 재현율이 크게 흔들린다는 것을 전략서에서 계산해 보고서야 이해했다.
- 배운 점: 대회의 평가 기준이 곧 설계 요구사항이다. 문제 정의를 먼저 해야 모델 선택이 흔들리지 않는다.

## 2. 데이터 확인과 탐색적 분석(EDA) (9/20 ~ 9/30)

**배경.** 데이터는 CN7·RG3 두 제품의 라벨 데이터(양품/불량)와 라벨 없는 데이터 4개 CSV로 구성되어 있었다. 라벨 데이터는 총 2,393행 중 불량이 42행으로 극단적으로 불균형했다.

**한 일.** 변수 분포 비교(KS 검정), 상관 분석, 군집 분석을 진행했다. CN7은 금형 온도가 높고 계량 시간이 짧은 영역에 불량이 몰리는 경향이 보였다(해당 영역 375행 중 불량 17건). RG3는 Ward, K-Medoids, K-Means로 군집을 나눠 봤지만 불량만 모이는 군집은 나오지 않았다. 상관분석 보고서의 용어가 어려워서 팀원용 용어해설집(게임 비유 방식)도 따로 만들었다.

가장 중요한 발견은 **라벨 충돌**이었다. 24개 입력값이 완전히 같은데 어떤 행은 양품, 어떤 행은 불량인 경우가 많았고, 불량 42건 중 36건이 이런 충돌 그룹에 속해 있었다.

**결과.** "입력이 같으면 모델은 같은 답을 낼 수밖에 없다"는 사실이 드러나면서, 행 단위로 정답을 맞히는 문제 설정 자체를 다시 봐야 한다는 결론에 이르렀다. CN7은 불량이 특정 영역에 모이는 신호가 있었고, RG3는 그런 신호가 약하다는 차이도 이 시점에 처음 보였다.

**회고.**
- 잘된 점: 모델부터 돌리지 않고 데이터 구조를 먼저 본 것. 라벨 충돌을 이 단계에서 발견하지 못했다면 이후 모든 검증이 중복 누수로 부풀려졌을 것이다.
- 어려웠던 점: 원본이 파일별로 이미 표준화되어 있어 수치를 물리 단위로 해석하기 어려웠고, 레짐 전환의 원인(설비·교대·금형 교체)은 데이터만으로 알 수 없었다.
- 배운 점: EDA에서 "신호가 없다"는 것도 결과다. RG3에서 불량 군집이 없다는 사실이 나중에 RG3를 모델 판정이 아닌 분포 감시로 운영하는 근거가 되었다.

## 3. 패턴 통합 전처리 (9/29 ~ 9/30)

**배경.** 같은 입력이 반복되고 라벨이 충돌하는 상황에서 행을 그대로 쓰면, 같은 입력이 학습과 검증 양쪽에 들어가 성능이 과대평가된다.

**한 일.** 24개 입력값이 완전히 같은 행을 하나의 "패턴"으로 묶고, 그 패턴의 라벨은 묶인 행 중 하나라도 불량이 있으면 불량, 즉 max(label)로 정했다. 이 라벨은 "제품 불량 확률"이 아니라 "이 공정 조건에서 불량이 나온 이력이 있다(위험 이력)"는 의미로 정의했다. 라벨 없는 데이터도 같은 방식으로 통합했다.

**결과.**

| 구분 | 원본 → 패턴 | 정상 / 위험 |
|---|---|---|
| CN7 라벨 | 1,211 → 606 | 592 / 14 |
| RG3 라벨 | 1,182 → 591 | 566 / 25 (위험 전부 충돌 패턴) |
| CN7 비라벨 | 35,239 → 28,771 | – |
| RG3 비라벨 | 35,941 → 29,707 | – |

**회고.**
- 잘된 점: 라벨의 의미를 "원본 제품 검사 결과 / 패턴의 불량 이력 / 모델 예측"으로 구분해 둔 것이 이후 보고서와 설명에서 과장된 주장을 막아 줬다.
- 어려웠던 점: 9/23 전략서에서는 행 단위 데이터에 그룹 ID를 붙여 StratifiedGroupKFold로 나누는 안을 먼저 설계했다. 이후 패턴 통합으로 방향을 바꾸면서 분할 숫자와 검증 설계를 다시 짜야 했다.
- 배운 점: 전처리는 "데이터를 깨끗하게 하는 일"이 아니라 "무엇을 예측할지 정하는 일"이다. 통합 방식 하나가 문제 정의를 바꿨다.

## 4. 학습·검증 전략 설계 (9/23 ~ 9/30)

**배경.** 위험 패턴이 CN7 14개, RG3 25개뿐이라 분할과 검증 방식에 따라 결과가 크게 흔들릴 수 있었다.

**한 일.** 9/23에 모델 이론·학습검증 전략서를 작성했다. LR은 해석 가능한 기준선, RF는 비선형 비교 모델, OCSVM은 이상 점수 보조 모델로 역할을 나눴다. 전처리(스케일러, 상수 변수 제거 등)는 학습 fold에서만 fit하고, 검증 라벨로 계수를 학습하지 않으며, 테스트는 한 번만 쓴다는 원칙을 정했다. 분할 seed를 결과가 좋게 나오는 값으로 바꾸지 않는다는 원칙도 적었다.

실제 구현에서는 패턴 단위로 seed 42 고정 분할을 했다(CN7 개발 484 / 테스트 122, RG3 개발 472 / 테스트 119). 개발셋은 4-fold OOF로 하이퍼파라미터와 임계값을 같이 골랐다.

**결과.** 모든 모델이 같은 분할·같은 OOF 기준으로 비교되었다. 다만 테스트셋은 이미 결과를 본 상태라 이후 문서에서는 "독립 테스트"가 아니라 "사후 관찰(historical_followup)"로 표시했다.

**회고.**
- 잘된 점: "검증에서 무엇을 봤는가"를 기록하는 습관. 이 덕분에 나중에 테스트셋 결과를 과장하지 않고 정직하게 표기할 수 있었다.
- 어려웠던 점: 원칙은 세웠지만 실험을 반복하면서 테스트 결과를 여러 번 보게 되었고, 결국 테스트의 독립성을 잃었다.
- 배운 점: 소표본에서는 검증 설계 자체가 결과보다 중요하다. 그리고 원칙은 문서로만 두지 말고 코드(고정 manifest)로 강제해야 지켜진다.

## 5. OCSVM 실험 (9/29 ~ 9/30)

**배경.** 정상 데이터만으로 정상 영역을 학습하고, 그 밖을 이상으로 보는 방식이 불량이 적은 데이터에 맞을 거라고 기대했다.

**한 일.** 입력 조합 7가지 × 하이퍼파라미터 616개 × 임계값 93개, 총 401,016개 조합을 OOF로 탐색했다. ν는 불량률이 아니라는 점, OCSVM 평가도 결국 라벨이 필요한 지도 평가라는 점을 전략서에 미리 정리해 두었다.

**결과.** CN7은 OOF F1 0.5까지 나왔지만 테스트에서는 위험 3개 중 0개를 찾았다. RG3는 테스트 위험 5개를 모두 찾았지만 오탐이 89개로 F1 0.101에 그쳤다. 결론적으로 OCSVM은 판정 모델이 아니라 보조 참고 점수로 내려갔다.

**회고.**
- 잘된 점: 40만 개 조합을 체계적으로 기록해 "운이 좋은 설정"이 아니라 "구조적으로 어렵다"는 결론을 근거 있게 낼 수 있었다.
- 어려웠던 점: 탐색 공간이 클수록 OOF에서 우연히 좋은 조합이 나온다. OOF 0.5가 테스트 0으로 떨어진 것이 그 예다.
- 배운 점: "정상 밖 = 불량"이 아니다. 이상(새로운 조건)과 품질 불량은 다른 개념이다.

## 6. 로지스틱 회귀(LR) 실험과 해석 (10/1 ~ 10/3, 직접 담당)

**배경.** TODO에 적었던 내 역할은 "로지스틱 해석 진행"이었다. LR은 계수로 변수의 방향을 설명할 수 있어서 대회의 XAI 요구에 가장 직접적으로 답할 수 있는 모델이었다.

**한 일.** 입력 조합·정규화 강도 C·클래스 가중치를 합쳐 240개 설정 × 임계값 1,001개를 탐색했다. 계수는 표준화 단위이고, 인과가 아니라 조건부 연관이라는 해석 원칙을 지켰다.

**결과.** CN7은 thermal 입력, C=10, 임계값 0.921에서 OOF F1 0.625가 나왔지만 테스트에서는 위험 3개 중 0개였다. RG3는 테스트 위험 5개를 모두 찾았지만 오탐이 110개였다. OOF 상위 10% 안에 위험이 몇 개 들어오는지 보면 LR은 11개 중 8개로 RF(9/11) 다음이었다.

**회고.**
- 잘된 점: 해석 가능한 기준선을 확보했고, LR 결과와 실행 코드를 원본 그대로 보존해(보존본 + 재현 감사) 이후 운영 코드를 고쳐도 LR 결과가 바뀌지 않았음을 증명할 수 있었다(재적합 차이 CN7 2.1e-12, RG3 3.9e-16).
- 어려웠던 점: OOF 성적이 가장 좋아 보였는데 테스트에서 하나도 못 찾은 것. 소표본 + 많은 탐색이 만든 착시였다.
- 배운 점: 한 임계값의 F1보다 "상위 몇 %를 검사하면 위험을 몇 개 찾는가" 같은 순위 지표가 소표본에서 더 안정적이다.

## 7. 랜덤 포레스트(RF) 실험 (10/3)

**배경.** LR이 선형 경계라 놓치는 비선형 조합을 RF가 잡을 수 있는지 확인하는 비교 모델로 계획했다.

**한 일.** 108개 설정 × 임계값 1,001개를 OOF로 탐색했다. RF는 OOB 점수를 쓰지 않았다. 중복 패턴 때문에 OOB가 누수될 수 있기 때문이다.

**결과.** CN7은 임계값 0.186에서 OOF F1 0.500, 테스트 위험 3개 중 0개. RG3는 임계값 0.297에서 OOF 0.116, 테스트 F1 0.111(위험 5개 중 1개, 오탐 12개). 반면 OOF 상위 10% 순위 기준으로는 RF가 11개 중 9개로 세 모델 중 가장 좋았다.

**회고.**
- 잘된 점: 임계값 하나의 F1이 아니라 순위 성능을 함께 본 덕분에, RF를 "임계값 판정 모델"이 아니라 "검사 우선순위 모델"로 쓰자는 결론에 도달했다.
- 어려웠던 점: 모델 세 개가 모두 CN7 테스트에서 0개를 찾았다. 처음에는 모델 문제라고 생각했지만, 테스트 위험이 3개뿐이라 판단 자체가 불안정하다는 것을 받아들여야 했다.
- 배운 점: 모델을 "맞다/틀리다"로 쓰지 않고 "어디부터 볼지" 정하는 도구로 쓰면 같은 모델도 현장 가치가 달라진다.

## 8. 모델 판정 가능성 검증과 제품별 운영 방식 결정 (10/3)

**배경.** CN7과 RG3에 같은 방식을 적용해도 되는지, 모델이 실제로 신호를 잡고 있는지를 따로 확인해야 했다.

**한 일.** 라벨을 섞어 우연히 나올 수 있는 성능과 비교하는 순열검정(permutation test)을 했다.

**결과.** CN7은 AUC 0.870, p=0.001로 모델이 진짜 신호를 잡고 있었다. RG3는 AUC 0.451, p=0.776으로 우연과 구분되지 않았다. 그래서 운영 방식을 둘로 나눴다.
- **CN7 — 모델 판정:** RF 점수 순서대로 정해진 검사 예산(정확히 k개)만큼 검사하고, 그 안에서 찾은 위험 수(found_TP)로 성능을 본다.
- **RG3 — 분포 감시:** 모델 판정 대신 불확실성(높음/중간/보류/낮음)과 Wilson 95% 구간으로 상태를 보고, 최소 20패턴·위험 5개가 모일 때까지는 판단을 보류한다.

**회고.**
- 잘된 점: "RG3는 지금 데이터로는 모델 판정이 불가능하다"고 정직하게 말한 것. 억지로 점수를 맞추지 않고 운영 방식을 바꾼 것이 이 프로젝트의 핵심 판단이었다.
- 배운 점: 한 가지 방식을 모든 제품에 적용하지 않는다. 데이터가 말해 주는 만큼만 모델에 권한을 준다.

## 9. 모델링 확장 아이디어 검토 (10/1)

**배경.** 통계·ML 외의 관점으로 차별화할 수 있는지 Codex와 Claude에게 각각 아이디어를 받았다.

**한 일.** Codex 쪽에서는 커리큘럼 학습(학습 순서), 능동학습(어떤 라벨을 먼저 확보할지), 비용 기반 의사결정(미탐·오탐·추가확인 비용), Group DRO(가장 약한 공정 조건 개선), 과학철학적 반증 설계를 제안받았다. Claude 쪽에서는 지속적 호몰로지 기반 레짐 탐지, Mapper 지형도, Betti 수 파생변수, Takens 임베딩 같은 위상수학 접근과 암묵지 인터뷰, 서사형 설명, 윤리 프레임, 혼합방법론 같은 인문학 접근을 받았다. 관계식 파생변수와 스태킹도 시도해 봤지만 성능은 개선되지 않았다.

**결과.** 위상수학(TDA)은 패턴 통합으로 시간 순서가 사라진 현재 구조와 맞지 않고, 반복 배열을 위상 구조로 착각할 위험이 있어 우선순위를 낮췄다. 대신 "확인된 라벨로 계속 학습한다", "검사 예산 안에서 무엇을 먼저 볼지 정한다"는 능동학습·의사결정론 관점이 운영 파이프라인 설계에 반영되었다.

**회고.**
- 잘된 점: 아이디어를 바로 구현하지 않고 "현재 아키텍처와 맞는가, 반증할 수 있는가"로 걸렀다.
- 아쉬운 점: 비용 기반 평가와 능동학습 실험은 시간 부족으로 실제 실행까지 가지 못했다. 현장 비용 정보도 없었다.
- 배운 점: 새로운 분야의 이름보다 "그 관점으로 어떤 규칙을 바꾸고, 무엇과 비교해 효과를 확인할지"가 중요하다.

## 10. 아키텍처 설계와 변천 (10/1 ~ 10/5)

**배경.** 단발성 모델 학습이 아니라, 현장에서 데이터가 계속 들어오고 정답이 쌓이는 구조를 보여 줘야 대회의 현장 적용 가능성·확장성에 답할 수 있었다.

**한 일.** 아키텍처 그림을 다섯 번 고쳤다.
1. EDA → 패턴 통합 → 분할 → 학습 → 사후 평가의 단발성 흐름
2. 배치 운영, 현장 정답 수집, 지속 학습, 배포 단계 추가
3. IF(Isolation Forest) 이상 점수 정렬과 가중치 순차 학습 아이디어 추가
4. 드리프트(분포 변화)를 재학습 시작점으로 사용
5. 7단계 구조로 개정 — 별도 "라벨 연결" 단계를 없애고 입력·판정·정답 수집·재학습·배포 흐름으로 정리

**결과.** 최종 구조는 "고정 참조 모델(IF) + 제품별 판정 모델 + 드리프트 감시 + 지속 학습(CT) + 배포 판단(CD)"의 7단계 운영 파이프라인이 되었다.

**회고.**
- 잘된 점: 그림을 고칠 때마다 "이 단계가 실제로 필요한가"를 물어서 단계를 줄였다(라벨 연결 단계 제거).
- 어려웠던 점: 그림이 바뀔 때마다 코드와 문서가 어긋났다. 팀장 검토에서 지적된 문제 상당수가 그림과 코드의 불일치에서 나왔다.
- 배운 점: 아키텍처 그림은 코드와 같이 버전 관리해야 한다.

## 11. 운영 파이프라인 구현 (10/3 ~ 10/5)

**배경.** TODO에서 내 남은 과제는 "5·6·7단계 구축 후 CD 보완, git push"였다.

**한 일.** 단계별로 다음 기능을 구현했다.
- **배치 수집과 중복 방지:** 들어온 데이터를 패턴 요약 해시로 식별하고, 저장 전에 예약을 먼저 걸어 같은 배치가 두 번 처리되지 않게 했다. 제품 ID 규칙은 기본 A(제품 ID 필수) + 예외 C(ID 없는 경우 내용 기반)로 정했다.
- **드리프트 감시:** 200개 제품(40패턴) 창으로 분포 거리(TV distance)를 재고, 부트스트랩 200회의 99% 분위수를 기준으로 1회 초과는 관찰(watch), 같은 기준에서 2회 연속이면 검토(review)로 올린다.
- **판정 계층:** CN7은 검사 예산 k개만큼 RF 순서로 지목, RG3는 불확실성 상태로 보고.
- **지속 학습(CT):** 현장 검토·원인·정답이 정상 30 / 위험 5 이상 모이면 전체 재학습.
- **배포 판단(CD):** 학습에 쓰지 않은 독립 평가 데이터(정상 30 / 위험 5 이상)로 평가하고, CN7은 도달 가능한 위험의 50% 이상을 찾고 현재 모델보다 좋을 때만 승격. 선택에 쓴 데이터로는 승격할 수 없다.
- **안전장치:** 운영 잠금 파일, 배포 전환 기록(준비→완료, 중단 시 재개), 롤백.

**결과.** 격리 환경에서 기능 검증을 마쳤다. 최종 확인 기준으로 테스트 122개와 LR 재현 감사가 통과했고, 실제 운영 모델·LR 결과·원본 데이터는 바뀌지 않았다. 다만 RG3 운영 기준선이 아직 없어 점검 스크립트는 "기준선 미준비(exit 1)"로 끝난다.

> 보고서 표기: **파이프라인 구현 및 격리 환경 기능 검증 완료. RG3 현장 검증과 운영 기준선 준비는 후속 단계로 남아 있음.**

**회고.**
- 잘된 점: 성능을 올리는 것보다 "잘못된 모델이 배포되지 않게 막는 장치"에 집중했다. 소표본에서 이게 더 현실적인 기여라고 생각한다.
- 어려웠던 점: 중복 방지, 재전송, 중간 실패 후 재개처럼 경계 상황이 끝없이 나왔다.
- 배운 점: 운영 코드는 "정상 흐름"보다 "실패했을 때 어떻게 되는가"가 대부분이다.

## 12. 검토 대응과 검증 체계 (10/5)

**배경.** 팀장님이 develop_seo 브랜치를 두 차례 검토했고, 드리프트 기록 누락, 정책 변경 시 연속 횟수 오류, 재전송 처리, 제품 ID 규칙 등이 지적되었다.

**한 일.** 지적 사항을 하나씩 수정하다가, 인접한 경우(파일 누락, 인덱스 손실, manifest 누락 등)를 계속 빠뜨리는 문제가 생겼다. 그래서 개별 수정 대신 **재전송 상황을 행렬로 펼친 테스트(226개 하위 사례)**로 전환했고, 구현은 Codex가 맡고 Claude가 검토하는 방식으로 역할을 나눴다. 런타임 원본 보존본과 AST 비교, 설정 재적합 감사로 LR 결과가 바뀌지 않았음을 매번 확인했다. PC에서 바로 실행할 수 있는 점검용 bat(ASCII 전용)와 안내 문서도 만들었다.

**결과.** 팀장 검토 항목(F01~F07, R01~R03)과 Codex 추가 지적이 모두 해결되었고, 최종 테스트 122개가 통과했다.

**회고.**
- 잘된 점: 원본 보존과 재현 감사를 먼저 만들어 둔 덕분에, 코드를 많이 고쳐도 "기존 결과는 그대로"라는 것을 증명할 수 있었다.
- 어려웠던 점: 하나씩 고치는 방식이 전체 그림을 놓쳤다. 같은 종류의 문제가 반복해서 지적되면서 시간이 많이 들었다.
- 배운 점: 버그를 하나 고칠 때 "이 버그와 같은 종류의 경우가 몇 개 더 있나"를 먼저 묻고, 경우의 수를 표로 만든 뒤 테스트로 한꺼번에 막아야 한다.

## 13. 협업 방식 (전 기간)

**배경.** 팀장(검토), 나(설계·LR 해석·운영 단계 담당), Codex(구현·검수), Claude(검토·수정·문서화)가 함께 작업했다.

**한 일.** 이미지 학습 → 코드 내 구현/미구현 확인 → 모델링 학습 → 맡은 부분 구현·테스트 → 5·6·7단계 구축 → CD 보완 → 기획서 초안 순서로 진행했다(TODO 메모). 후반에는 "Codex가 구현, Claude와 Codex가 교차 검수, 내가 PC에서 실행·확인, 팀장님이 최종 검토"라는 흐름이 자리 잡았다.

**회고.**
- 잘된 점: AI 도구 두 개를 서로 검수시키면서 한쪽이 놓친 문제를 다른 쪽이 잡았다.
- 어려웠던 점: 내가 "해 줘"만 하다 보니 코드와 프로젝트 전체에 대한 이해가 뒤처졌다. 결과를 설명해야 할 때 내가 직접 이해하고 있지 않으면 검토 대응이 어렵다는 걸 느꼈다.
- 배운 점: AI에게 맡기더라도 설계 의도와 핵심 수치는 내가 설명할 수 있어야 한다. 각 단계마다 "왜 이렇게 했는가"를 내 말로 정리해 두는 것이 필요하다.

## 15. 전체 회고 한 문단

이 프로젝트에서 가장 크게 배운 것은 "데이터가 말해 주는 만큼만 주장한다"는 태도였다. 처음에는 좋은 F1을 내는 모델을 찾으려 했지만, 라벨 충돌과 극소수 불량 때문에 어떤 모델도 테스트에서 안정적인 판정을 보여 주지 못했다. 그래서 문제를 패턴의 위험 이력 예측으로 다시 정의하고, 신호가 확인된 CN7에는 검사 우선순위 모델을, 신호가 없는 RG3에는 분포 감시를 적용했으며, 성능을 억지로 올리는 대신 현장 정답이 쌓일 때 안전하게 다시 배우고 검증된 경우에만 배포하는 운영 구조를 만들었다. 아쉬운 점은 실행과 수정을 AI에게 많이 맡기면서 내 이해가 늦게 따라왔다는 것이고, 다음에는 각 단계의 설계 이유를 내가 먼저 정리한 뒤 구현을 맡기려 한다.
