KAMP 팀장 검토 — 쉬운 설명 (수정 이유와 방향)

[한 줄 요약]
모델 성능 얘기가 아님. "파이프라인이 실수·장애 상황에서도 자료를 정확히 한 번만 세고, 상태를 헷갈리지 않게 보여주는가"에 대한 지적.
코드는 다 만들어져 있지만, 예외 상황에서 숫자가 틀어지거나 화면 표시가 오해를 부를 수 있는 곳이 7군데 있음.

[비유: 택배 물류센터]
배치 = 택배 상자, 드리프트 감지 = "요즘 들어오는 물건이 평소와 다른가" 확인, 검사 예산 = "상자당 10%만 열어볼 수 있음".

A. 같은 자료를 두 번 세는 문제 (F01·F02·F03)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
왜 중요한가
  같은 배치가 두 번 들어가면 드리프트 감지가 "변화 2회 연속" → review(원인 검토)로 잘못 올라갈 수 있고,
  재학습 자료에도 같은 제품이 두 번 들어감. 공정은 그대로인데 시스템은 바뀌었다고 판단.

F01 행 순서만 바뀐 같은 파일을 다른 파일로 착각
  상황: 같은 파일을 엑셀에서 정렬만 바꿔 다시 보냄.
  원인: 중복 확인용 "내용 지문(해시)"을 만들 때 행 순서가 지문에 섞여 들어감. 내용은 같은데 지문이 달라짐.
  특히 제품 ID 열이 없는 파일은 이 지문이 유일한 중복 검사라서 그대로 통과함.
  방향: 순서와 상관없는 지문으로 바꿈 → "패턴별 제품 수·정상 수·불량 수" 요약표로 지문 생성.
  주의: 내용이 같다고 무조건 같은 배치는 아님(다른 날 같은 조건 생산 가능).
        제품 ID·전달 ID를 1차 근거로, 내용 지문은 보조 근거로. ID 없는 경우는 "중복 의심 보류" 정책을 정해야 함.

F02 저장은 됐는데 감지 단계에서 오류
  상황: 배치 저장 → 원장(장부) 기록 → 드리프트 감지 중 오류 → 사용자는 "실패" 메시지를 받음.
  실제: 장부에는 이미 들어가 있음. 그런데 중복 방지 목록에는 등록이 안 됨.
  결과: 사용자가 실패한 줄 알고 다시 보내면 한 번 더 등록됨. 같은 batch_id로 다시 보내면 아예 오류로 멈춤.
  방향: "받았다(수집 완료)"와 "감지·안내까지 끝났다(처리 완료)"를 다른 상태로 기록.
        재시도 시 이미 받은 배치는 다시 저장하지 말고, 못 끝낸 뒤 단계(감지·안내)만 다시 실행.
        중복 방지 목록 등록은 수집 확정과 같은 시점에 함.

F03 두 작업이 동시에 같은 배치를 받음
  상황: 두 프로그램이 동시에 "이 배치 처음 보네?" 확인 → 둘 다 등록.
  원인: "확인"과 "등록" 사이에 틈이 있음(잠금이 둘을 한 번에 묶지 않음).
  방향: 확인→등록을 하나의 잠금 안에서 처리. 지금처럼 혼자 로컬에서 실행하면 실제 발생 가능성은 낮아 후순위.

B. 화면·결과 표시가 오해를 부르는 문제 (F04·F05)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
F04 "아직 판단 못 함"이 "불확실성 낮음"으로 표시
  상황: 배치가 작아 감지 표본이 모자람 → 드리프트 상태 waiting(모으는 중).
  문제: RG3 제품 안내에서는 이걸 불확실성 "낮음"으로 보여줌. 현장은 "괜찮다"로 읽음.
  비유: 건강검진 결과가 아직 안 나왔는데 "이상 없음" 도장을 찍는 것.
  방향: waiting을 "판단 대기"라는 별도 단계로 표시. 코드 몇 줄 수정.

F05 "10%만 검사"인데 10개 전부 검사 대상으로 표시
  상황: 제품 10개, 검사 비율 10% → 1개만 검사해야 함. 그런데 10개 점수가 모두 같음(동점).
  현재 실행: 동점이면 전부 표시 → 10개 검사 대상.
  현재 평가: 동점 중 1개를 무작위로 고른다고 가정 → 기대 발견 0.1개.
  문제: 실제 운영과 평가가 서로 다른 규칙을 씀 → 평가 숫자가 실제 운영을 대변하지 못함.
  CN7은 같은 입력 패턴 제품이 많아(1,211행 → 606패턴) 같은 점수가 흔함 → 자주 생길 수 있음.
  또 배치 안내는 "제품 수" 기준 10%, 평가는 "고유 패턴 수" 기준 10% → 같은 10%라도 뜻이 다름.
  방향: 동점 처리 규칙 하나를 정해서 실행과 평가에 똑같이 적용.
        (안 1) 정확히 k개만: 동점이면 record_id 순 등 재현 가능한 규칙으로 자름
        (안 2) 동점 전부 검사: 실제 검사량이 예산을 넘는 걸 기록하고 평가도 그 기준으로
        제품 단위/패턴 단위 결과를 따로 기록.

C. 기록이 정책·용도를 정확히 보존하지 못하는 문제 (F06·F07)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
F06 경보 기준을 바꿨는데 예전 경보선을 그대로 씀
  상황: 경보 민감도(drift_quantile)를 0.99 → 0.95로 바꿈.
  문제: 경보선 계산 결과를 저장한 파일 이름에 이 값이 없음 → 이전 0.99 결과 파일을 그대로 다시 읽음.
  결과: 설정은 바꿨는데 실제 판정은 예전 기준. 나중에 "왜 이 판정이 나왔나" 추적 불가.
  방향: 파일 이름·내용에 분위수, 기준선 ID, 코드 버전을 함께 기록.

F07 평가 자료의 "용도"가 바뀌어도 모름
  상황: 평가 자료에는 용도 기록이 있음
        independent(처음 보는 독립 평가 → 승격 근거 가능) / historical_followup(이미 본 자료 → 승격 근거 불가)
  문제: 평가 CSV 파일은 지문으로 보호하지만, 용도가 적힌 manifest 파일은 보호 안 함.
        누가 historical_followup을 independent로 고치면 원래 막혀야 할 승격이 통과될 수 있음.
  방향: 전처리를 다시 하자는 게 아님. 평가 파일과 용도 기록을 함께 지문으로 묶어 두고, 승격할 때 대조.

D. 운영 준비 상태
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
CN7 RF가 아직 운영 모델로 지정 안 됨
  현재 운영 장부에는 IF(기준 모델)만 있음 → CN7 검사 우선순위가 실제로는 안 만들어짐(no_active_model).
  방향: initial(RF 생성) → initialize(운영 지정) → baseline(기준선 생성)을 명시적으로 실행.

동일 환경 종단 리허설
  팀장 PC는 라이브러리 버전이 달라 저장 모델 확인 일부가 실패함(모델 문제가 아니라 환경 문제).
  방향: 고정된 라이브러리 버전에서 처음부터 끝까지 한 번 실행
        초기 모델 → 배치 → watch/review → 재학습 후보 → 평가 → 승격/유지 → 롤백.
  정상 경로뿐 아니라 실패 경로(중복 배치, 감지 실패, 평가 미달 등)도 확인.

E. 오해하지 말아야 할 것
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- 전처리 정책(24개 입력 동일 패턴 통합, max(label))은 그대로 유지. 바꾸라는 지적 아님.
- 새 변수 추가·성능 튜닝 요구 아님.
- TV 거리·Wilson 구간 설명은 "왜 이 통계를 썼는가" 보완 설명이고 문제 지적 아님.
  TV 거리 = 두 분포가 얼마나 다른지 0~1로 나타낸 값(불량 확률 아님)
  Wilson 구간 = 관측 수가 적을 때 비율이 얼마나 불확실한지 보여주는 범위
