2. 1차 수정 — 팀장 검토 F01~F07
========================================================================
F01 같은 파일을 행 순서만 바꿔 다시 보내면 새 파일로 착각
  원인: 중복 확인용 지문에 행 순서가 섞여 들어감
  수정: 패턴별 요약(제품 수·정상 수·불량 수·대표 라벨)으로 지문 생성 → 순서와 무관
        제품 ID가 1차 근거. ID 없고 내용 같으면 '중복 의심' 보류
        ID가 모두 새롭고 내용만 같으면 다른 생산 건으로 수집하고 duplicate_note에 기록

F02 저장은 됐는데 감지 단계에서 오류 → 재전송 시 두 번 등록, 같은 ID면 오류로 멈춤
  수정: 수집 확정 → 분포 감지 → 검사 안내를 단계로 나눠 batches/<ID>/processing.json에 기록
        실패해도 수집은 유지. 같은 batch_id 재전송 또는 resume → 못 끝낸 단계만 재실행
        다른 batch_id로 재전송 → 중복으로 보류
        같은 batch_id에 다른 내용 → conflict로 거부(기존 배치 보호)
        보류(held)된 배치는 같은 batch_id로 다시 보낼 수 있음(이전 시도는 held_archive에 보관)
        이미 끝난 배치를 다시 보내면 already_completed로 알리고 변경 없음

F03 두 작업이 동시에 같은 배치 등록 가능
  수정: 수집 전용 잠금(.ingest.lock) — 중복 검사부터 등록·감지·안내까지 한 번에 하나만 실행
        남은 잠금 해제: unlock --lock ingest --reason <사유>

F04 표본 부족(waiting)이 '불확실성 낮음'으로 표시
  수정: '판단 대기(pending)' 단계로 분리. 범위 밖 값·정보 부족 같은 제품 근거는 그대로 높음/중간

F05 검사 10%인데 동점이면 전부 표시, 평가는 다른 가정
  수정: 동점 규칙 cn7_tie_rule 도입 — 기본 exact_k(정확히 예산 수), 선택 all_ties(동점 전부 + 초과 수 기록)
        (2차에서 선택 순서와 평가 계산까지 완전히 일치시킴 → 아래 3장)

F06 경보 기준(분위수)을 바꿔도 예전 경보선 재사용
  수정: 경보선 캐시에 분위수·반복 수·기준선·코드 해시 서명 기록
        다르면 예전 캐시를 calibration_archive로 옮기고 다시 계산. 드리프트 결과에도 서명 기록

F07 평가 자료의 용도(purpose)가 바뀌어도 모름
  수정: 등록 시 manifest 지문을 manifest_integrity.json에 고정, 평가·승격 때 대조
        바뀌었으면 평가·승격 거부. 이 기능 도입 전 등록 자료는 재등록 필요

3. 2차 수정 — Codex 검수 지적 3건
========================================================================
[1] 수집 확정 도중 실패 시 중복 수집 가능 (높음)
  원인: 파일·장부 저장 후 중복 방지 목록을 기록 → 그 사이 실패하면 처리 상태 파일이 없어
        pending에 안 보이고, 다른 batch_id로 같은 자료가 다시 수집됨 (Claude 환경에서도 재현)
  수정: 중복 방지 목록에 먼저 '예약'을 기록한 뒤 파일·장부 저장
        - 예약 기록 실패 → 아무것도 저장 안 됨
        - 이후 어느 단계에서 실패해도 같은 내용·제품 ID는 다른 batch_id로 보류
        - pending에 commit_incomplete(파일 저장됨) / reserved_not_stored(저장 전 중단)로 표시
        - 같은 batch_id 재전송 또는 resume → 빠진 장부·처리 상태를 채우고 끝까지 처리, 완료 후 예약 삭제
        - 기본 수집이 보류로 끝나면 예약 되돌림
  검증한 장애 지점 4곳: 예약 기록 / 기본 장부 기록 / 처리 상태 기록 / 장부 뒤 중복 색인 기록

[2] CN7 동점: 실제 선택(ID 순)과 평가(무작위 기대값)가 다름 (높음)
  수정: 실행과 평가가 같은 순서로 선택
        점수 높은 순 → 입력 패턴 지문(fingerprint) 순 → record_id 순 (라벨 미사용)
        평가 판정 지표를 found_TP(실제로 고른 패턴의 위험 수)로 변경. 승격·선정 비교도 found_TP 사용
        무작위 동점 기대값은 random_tie_expected_TP/min/max로 참고만 기록
        배치는 제품 단위, 평가는 고유 패턴 단위 → 결과에 unit으로 표시

[3] 검사 비율 0%를 허용하지만 실제로는 1개 검사 (보통)
  수정: 0%는 금지로 통일(0 초과 1 이하만 허용). CLI·Operations·계산 함수 모두 동일
