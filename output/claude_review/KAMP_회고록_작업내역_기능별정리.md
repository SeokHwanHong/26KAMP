## 2. 기능별 정리

각 기능은 **무엇을·왜 → 언제 → 어떻게 → 결과·검증 → 회고 포인트** 순서로 정리했다.

### 2.1 데이터 전처리 — 패턴 통합과 위험 이력 라벨

- **무엇을·왜**: 같은 공정값에서 합격·불합격이 섞여 나오는 데이터라서, 행 단위로 학습하면 같은 입력에 정답이 둘인 모순이 생긴다. 24개 입력이 완전히 같은 제품을 하나의 패턴으로 묶고, 불량이 한 번이라도 있으면 위험 패턴으로 정의했다.
- **언제**: 9/29 (문서 갱신 10/2)
- **어떻게**: 반올림·대체·삭제 없이 완전 일치만 통합하고, 원본 행 → 패턴 연결표와 정상·불량 관측 수를 보존했다. 저장 후 다시 읽어 원본 입력 복원까지 검증했다. 비라벨은 라벨을 만들지 않고 따로 보관했다.
- **결과**: CN7 606패턴(정상 592·위험 14), RG3 591패턴(정상 566·위험 25). RG3 위험 25개는 전부 정상·불량이 공존하는 조건이다.
- **회고 포인트**: 예측 목표가 "제품 불량"이 아니라 "불량 이력이 있는 조건"으로 바뀐다는 점을 이해하는 것이 이후 모든 해석의 출발점이었다.

### 2.2 평가 원칙 — 고정 분할과 OOF

- **무엇을·왜**: 불량이 1~2%뿐이라 평가 자료를 잘못 쓰면 성능이 쉽게 부풀려진다.
- **언제**: 9/29
- **어떻게**: 패턴 단위로 Test 20%를 고정하고, 개발 80%는 4-fold 교차검증(OOF)으로 모델·임계값을 골랐다. 변환(scaler·PCA)은 각 fold의 train에서만 적합했다.
- **결과·한계**: Test를 여러 번 확인하면서 결국 독립 시험지가 아니게 되었다. 이후 운영 단계에서는 "이미 본 Test는 승격 근거로 쓰지 않는다"는 규칙으로 이어졌다.
- **회고 포인트**: 시험지를 한 번 보면 되돌릴 수 없다. 최종 판단용 독립 자료가 따로 필요하다.

### 2.3 탐색 실험 — 관계식·잔차, 스태킹, 학습 아키텍처 아이디어

- **무엇을·왜**: 기본 모델의 한계를 넘기 위해 변수 관계식의 잔차, 모델 스태킹, 짧은 과거 문맥을 시도했다. 교육학(커리큘럼 학습)·정보이론(능동학습)·의사결정론(오류 비용)·집단별 강건 최적화 관점의 확장 아이디어도 정리했다.
- **언제**: 10/1
- **결과**: 관계식은 변수 관계는 잘 잡았지만(R² 높음) 불량 구분 개선은 입증하지 못했다. 스태킹도 개발 검증의 일부 개선이 Test의 안정적 개선으로 이어지지 않았다.
- **회고 포인트**: 높은 R²는 "다른 변수로 값을 잘 맞힌다"는 뜻이지 분류 성능이 아니다. 개선이 없다는 결과도 그대로 기록한 것이 이후 방향 전환의 근거가 되었다.

### 2.4 모델 학습 — IF, OCSVM, 로지스틱 회귀(LR), 랜덤 포레스트(RF)

- **무엇을·왜**: 정상만 배우는 모델(IF·OCSVM)과 정상·불량을 함께 배우는 모델(LR·RF)을 비교했다.
- **언제**: IF·OCSVM 10/2, LR 10/3 오전(사용자 담당), RF 비교 10/3 오후
- **어떻게**
  - IF는 고정 참조로 지정했고, OCSVM은 노트북에서 탐색해 후보로 저장했다.
  - LR은 입력 구성 8 × C 15 × 가중치 2 = 240개 설정을 각각 임계값 1,001개로 OOF 탐색했다(총 480,480행 재검산).
  - RF는 고정 설정(나무 300·깊이 5·잎 최소 5·불균형 보정)이다.
- **결과**
  - CN7 LR: OOF F1 0.625였지만 Test 위험 3개를 모두 놓쳤다.
  - RG3 LR: Test 위험 5개를 다 찾았지만 정상 114개 중 110개를 경보 처리했다.
  - OCSVM도 CN7 0/3, RG3 오탐률 78%로 비슷했다.
  - 반면 "위험한 순서로 줄 세우기"는 CN7에서 양호했다. 개발 OOF 상위 10% 검사 시 위험 11개 중 RF 9개, LR 8개, OCSVM 4개를 찾았다.
- **검증 보완**: OCSVM 후보 등록 시 감사 기록과 모델 해시·임계값을 대조하지 않던 문제와, 실행 결과가 덮어써지던 문제를 고정 run_id 폴더로 보완했다.
- **회고 포인트**: 고정 임계값 판정은 실패했지만 순위는 의미가 있었다. "불량/정상 판정"에서 "검사 우선순위"로 문제를 다시 정의하게 된 계기였다.

### 2.5 데이터 유형 분기 — CN7은 모델 판정, RG3는 분포 감시

- **무엇을·왜**: 두 제품에 같은 방식을 쓰는 것이 맞는지 통계로 확인했다.
- **언제**: 10/3 오후
- **어떻게**: 개발 OOF에서 단순 구간 위험 이력 점수에 대해 순열 검정을 했다.
- **결과**: CN7은 AUC 0.870(p=0.001)로 신호가 있었고, RG3는 AUC 0.451(p=0.776)로 무작위와 구분되지 않았다.
  - CN7: RF + 검사 예산(배치마다 위험 점수 상위 10%만 검사)
  - RG3: 판단 불확실 단계(높음·중간·판단 대기·낮음)와 추가 검사 안내. 불량 확률은 제공하지 않는다.
- **회고 포인트**: "모든 데이터에 같은 모델"이 아니라 "데이터가 말해 주는 만큼만 판단한다"는 원칙을 세웠다. RG3에서 확률을 제공하지 않기로 한 것이 오히려 정직한 선택이었다.

### 2.6 RG3 구간 안내 — Wilson 구간과 표본 부족 표시

- **무엇을·왜**: RG3는 모델로 가를 수 없으므로, 어떤 공정 구간에서 위험 이력이 관측됐는지를 근거와 함께 보여 주기로 했다.
- **언제**: 10/3
- **어떻게**: 학습 자료로 고정한 구간마다 패턴 수, 위험 수, 관측 비율, Wilson 95% 구간을 표시했다. 참조 20패턴·위험 5개 미만이면 "표본 부족"으로 표시했다.
- **시행착오**: 처음 규칙(위험이 1건이라도 있는 구간이면 재검사)은 RG3 Test 119개 전부를 재검사로 판정해 쓸모가 없었다. 위험 이력은 참고 표시로만 남기고, 재검사 권고는 "학습 범위 밖·정보 부족·분포 변화"에 근거하도록 바꿨다.
- **회고 포인트**: 0건을 안전으로 읽지 않는 것, 그리고 "보수적 안내"가 검사량을 전혀 줄이지 못하면 의미가 없다는 것을 함께 배웠다.

### 2.7 7단계 운영 파이프라인 — 배치·드리프트·재학습·교체·롤백

- **무엇을·왜**: 공장은 계속 생산하고 분포는 바뀐다. 아키텍처 5번 그림에 맞춰 학습 이후의 운영 순환을 구현했다.
- **언제**: 골격 10/2, 구현 10/3(Codex), 보완 10/5
- **어떻게**
  - 배치 수집 시 입력·좌표·라벨을 검증하고, 저장 모델로 추론한다(변환 재적합 없음).
  - 제품 200개·패턴 40개를 모아 TV 거리를 계산하고, 재표집 200회의 99% 지점을 경보선으로 쓴다. 초과 1회면 watch, 2회 연속이면 review다.
  - review + 원인 기록 + 라벨 + 최소 표본을 갖췄을 때만 후보를 재학습한다.
  - 분리 평가를 통과한 모델만 승격하고, 롤백할 수 있다.
- **결과**: 격리 환경에서 초기 기준 → 배치 → watch/review → 원인 확인 → 후보 → 평가 보류·유지 → 승격 → 롤백까지 종단 리허설에 성공했다.
- **회고 포인트**: 재학습을 자동으로 하지 않는 것, 공정 이상을 새 정상으로 흡수하지 않는 것이 이 구조의 핵심 안전장치였다.

### 2.8 중복·재전송 처리 — 같은 자료는 정확히 한 번만

- **무엇을·왜**: 같은 배치가 두 번 들어오면 공정은 그대로인데 "변화 2회 연속"으로 오판해 재학습까지 열린다.
- **언제**: 10/3 첫 구현, 10/5 집중 보완(F01, Codex 검수 다수, R02)
- **어떻게 (발전 과정)**
  1. 행 순서에 따라 달라지던 내용 지문을 패턴 요약 지문으로 바꿨다.
  2. 저장 전에 중복 색인에 먼저 예약해서, 중간에 멈춰도 다른 ID로 재수집되지 않게 했다.
  3. "제품 ID–입력–라벨" 연결 지문을 두고, 저장된 제품 파일에서 다시 계산해 비교하게 했다.
  4. 제품 ID 계약을 정했다. A(고유 생산 ID)를 기본으로, C(ID 없음)를 예외 경로로 둔다.
  5. 증거가 손상되면 짐작하지 않고 거부한다.
- **결과**: 재전송 판단을 226개 조합(ID 출처 × 재전송 유형 × 처리 단계 × 기록 손상)으로 검증했다.
- **회고 포인트**: 이 기능에서 결함이 가장 많이 나왔다. 사례 하나씩 고치다 매번 옆 사례에서 다시 깨졌고, "상태·증거 표를 먼저 만들고 조합 전체를 테스트한다"는 방식으로 바꾼 뒤에야 정리됐다.

### 2.9 장애 복구와 재개 — 멈춘 곳부터 같은 근거로

- **무엇을·왜**: 저장은 됐는데 감지가 실패하면, 다시 보낼 때 두 번 집계되거나 멈춰 버렸다.
- **언제**: 10/5 (F02, R01, P1)
- **어떻게**
  - 수집 확정 → 감지 → 안내 단계를 처리 상태 파일에 기록하고, `resume`이나 같은 ID 재전송으로 남은 단계만 처리한다.
  - 감지 결과는 저장됐는데 소비 장부가 실패한 경우, 감지 ID 기준으로 한 번만 반영한다(R01). 이를 위해 공통 코드를 최소한으로 수정하고 원본을 보관했다.
  - 안내를 재개할 때는 처음 기록한 모델·기준선·정책을 고정해 쓴다.
  - 판단 대기 배치가 나중에 감지되면 새 안내판을 만들고, 처음 안내는 이력으로 보존한다.
- **회고 포인트**: "다시 처리"와 "이어서 처리"는 다르다. 재처리가 상태를 두 번 바꾸지 않게(멱등성) 하는 것이 운영 코드의 핵심이었다.

### 2.10 판단 표시와 검사 예산 규칙

- **무엇을·왜**: 표시가 틀리면 현장이 잘못 읽는다.
- **언제**: 10/5 (F04, F05, Codex 검수, R03)
- **어떻게**
  - 표본이 부족한 waiting을 "불확실성 낮음"이 아니라 "판단 대기"로 표시했다.
  - 검사 10%면 정확히 k개만 고르고, 동점이면 입력 지문 → 제품 ID 순으로 정했다. 평가도 같은 규칙의 실제 선택 결과(found_TP)로 계산한다.
  - 검사 비율 0%는 금지했다.
  - 동점을 전부 검사하는 모드(all_ties)는 검사량이 달라지므로 참고 전용으로만 쓰고, 선정·승격 근거로는 쓰지 않는다.
- **회고 포인트**: 실행 규칙과 평가 규칙이 다르면 평가 숫자는 실제 운영을 대변하지 못한다.

### 2.11 기록 보호 — 경보선 캐시, 평가 자료, 모델 교체

- **무엇을·왜**: 설정을 바꿨는데 예전 계산을 쓰거나, 평가 자료의 용도가 바뀌거나, 교체가 중간에 멈추면 근거가 어긋난다.
- **언제**: 10/5 (F06, F07, P1-4, P2-1)
- **어떻게**
  - 경보선 캐시에 정책 서명을 붙이고, 정책이 바뀌면 다시 계산한다.
  - 평가 자료는 목적·지문·해시를 고정하고, 같은 자료의 재등록이나 선정 자료와 겹치는 패턴은 승격 근거에서 제외한다.
  - 모델 교체는 새 기준선을 먼저 준비한 뒤 함께 전환한다. 실패하면 운영을 막고 같은 전환을 재개한다.
  - 모든 운영 작업에 공통 잠금을 건다.
- **회고 포인트**: 해시는 "기록 불일치를 탐지하는 수단"이지 변조를 막는 인증 장치가 아니라는 한계도 함께 명시했다.

### 2.12 검증 체계 — 테스트, LR 감사, 검사 실행기

- **무엇을·왜**: 고칠 때마다 다른 곳이 깨지지 않았는지 한 번에 확인해야 했다.
- **언제**: 10/3 통합 실행기, 10/5 확장
- **어떻게**
  - `run_checks`로 운영·등록·OCSVM·판정·운영 계층 테스트와 LR 감사를 한 번에 돌린다.
  - 공통 코드를 수정한 뒤에도 과거 LR 기록을 고치지 않도록, 원본 보관본으로 출처를 확인하고 선택 설정을 다시 학습해 재현하는 방식으로 감사를 바꿨다.
  - `run_checks_only`는 운영 상태를 바꾸지 않고 회귀 결과와 운영 준비 상태를 따로 판정한다.
- **결과**: 테스트 수가 43(10/3) → 61 → 122(10/5)로 늘었다. 최종 회귀는 전부 통과했고, 실행기는 RG3 기준선 미준비를 "운영 준비 미완료"로 정상 판정했다.
- **회고 포인트**: 실행 환경이 다르면 검증도 달라진다. Claude는 PC에서 직접 실행할 수 없어 bat 파일로 우회했고, 이 제약이 검증 속도를 떨어뜨렸다.

### 2.13 협업 방식 — 팀장 검토와 AI 교차 검수

- **무엇을·왜**: 한 명(한 AI)이 만들고 스스로 검증하면 빈틈을 놓친다.
- **언제**: 10/3 ~ 10/5
- **어떻게**
  - 팀장님이 브랜치를 보고 통계·논리·흐름을 두 번 검토했다.
  - Claude가 검토 내용을 코드와 대조해 수정했다.
  - Codex가 일부러 장애를 주입해 검수했다(5회 이상).
  - 이후 구현은 Codex, 설계 검토·보고서 정리는 Claude로 역할을 나눴다.
- **결과**: 팀장 지적 F01~F07, R01~R03과 정적 지적을 모두 반영했고, 검수에서 나온 추가 결함 10여 건을 보완했다.
- **회고 포인트**: "고치는 쪽"과 "깨뜨려 보는 쪽"을 나누니 결함이 빨리 드러났다. 반대로 고치는 쪽이 공격자 시점을 갖지 않으면 같은 유형의 결함이 반복된다는 것도 확인했다.
