Codex 수정 프롬프트(7단계 아키텍처 추가검토 반영) — Claude 의견 (2026-10-05)

[총평]
방향은 동의. 팀장 PDF의 R01~R03과 정적 지적을 빠짐없이 옮겼고, 금지사항(실제 runtime 변경 금지, 해시 검증 삭제 금지,
튜닝·모델 추가 금지, 미실행 결과를 통과로 보고 금지)도 적절함. 다만 아래 6가지는 시작 전에 정하는 게 좋음.

1. 한 번에 하기엔 범위가 큼 → 단계로 나눠 진행 제안
   R01~R03 외에 버전 고정, waiting 후속 연결, 잠금 통일, 기준선 전환 복구, 평가 재등록 이력, 실행기, 문서, 종단 리허설까지
   사실상 한 라운드 전체. 지금까지 매 라운드 Codex 장애 주입에서 새 경계 사례가 나왔으므로 한 번에 다 바꾸면
   회귀 위험이 크고 검수도 어려움.
   제안:
     1차(P0): R01, R02(+key=None 경로), R03, 실행기 종료 코드·검사 전용 실행기 분리 → Codex 검수
     2차(P1): 버전 고정(안내 재개), waiting 후속 연결, 잠금 통일, 승격/롤백 기준선 실패 복구 → 검수
     3차(P2): 평가 지문 재계산·재등록 이력·선정 자료 겹침, 문서(7단계 진입점) → 검수
     마지막: CN7/RG3 격리 state-root 종단 리허설(J)

2. pipeline_runtime.py 수정 허용 범위 — 결정 필요
   프롬프트는 "꼭 필요하면 최소 범위 변경, 우회 계층을 계속 쌓지 마"라고 함 → R01은 원본 detect에서
   감지 기록과 소비 장부를 함께 확정하는 게 맞는 해결이라고 봄(판정 계층 우회보다 근본적).
   부작용: audit_logistic_runs.py 19행(저장된 LR 실행의 runtime 코드 해시 == 현재 파일)이 실패함.
   프롬프트는 "과거 기록 수정·해시 검증 삭제 금지, 과거 출처 보존과 새 코드 검증 분리"를 요구하므로 방법은:
     - 변경 전 pipeline_runtime.py를 해시 이름으로 보관(출처 보존)하고, 감사는 "기록된 해시 = 보관본" 확인
     - 추가로 학습 경로 함수(fit_supervised 등)의 소스가 보관본과 현재가 같은지 확인 → 학습 결과 불변 근거
     - LR 탐색 재실행은 하지 않음(프롬프트도 대규모 재학습 반복 금지)
   운영 모델은 영향 없음(모델 로드는 이 해시를 보지 않음).

3. 검증 환경의 한계 — 미리 합의
   Claude 클라우드 환경에서는 판정 계층 테스트와 합성 종단 리허설은 직접 실행 가능.
   전체 검사(LR 감사·기존 OCSVM 회귀)는 대용량 실행 결과가 PC에 있어 사용자 PC에서 실행해야 함.
   Claude는 PC 터미널 입력 불가 → bat 더블클릭 방식 유지.
   프롬프트의 "기존 실행기(RF 등록 포함) 무심코 실행 금지"에 맞춰 검사 전용 실행기(run_checks_only.bat)를 새로 만들어 분리할 것.

4. 제품 ID 계약 — 사용자/팀 결정 필요
   R02와 "ID 발급 주체·고유 범위 명시"는 코드만으로 정할 수 없음. 대회 데이터에는 생산 ID가 없음.
   제안 기본값: product_id는 데이터셋(cn7/rg3) 안에서 전역 고유, batch_id는 전송 이벤트 ID.
   ID 없는 자료는 기존 호환 경로(내용 해시로 중복 의심 보류)로 분리하고 한계를 문서에 명시.
   파일 내부 행 번호(batch:i)는 전역 제품 ID로 취급하지 않음(현재도 비교에서 제외 중).

5. 범위를 줄이면 좋을 부분
   - 5장 "새 버전으로 재산출 revision 기능": 이번엔 "최초 버전 고정, 없으면 실패 명시"까지만 하고 재산출 기능은 보류 제안
   - 3장 라벨 정정: 프롬프트대로 거부·안내 + 요구사항 문서화만(인터페이스 구현은 하지 않음)
   - 4장 all_ties: 선정·승격에서 거부, 배치 결과 열람용으로만 유지(초과 검사 수 표시)

6. 잠금 통일 방식 제안(6장)
   잠금 하나를 "운영 작업 잠금"으로 정하고 ingest·detect·promote·rollback이 모두 먼저 획득 → 그 안에서만 writer 잠금.
   획득 순서가 항상 같아 교착 없음. 현재 규모(로컬 단일 PC)에서는 직렬화가 적절하다는 프롬프트 판단에 동의.

[프롬프트에서 특히 좋은 점]
- key=None(입력 검증 실패)일 때 내용 비교를 건너뛰고 성공 응답하지 말라는 지적: 현재 코드에서 실제로 그런 경로가 있음
  (완료 배치 재전송 시 좌표 미확인 등으로 key가 없으면 _retry가 비교 없이 already_completed/재개). 반드시 반영.
- ID 집합만 비교하지 말고 "제품 ID-입력-라벨 연결"을 비교하라는 것: 현재 예약 비교도 ID 집합 + 내용 요약이라
  ID별 입력 맞바꿈은 못 잡음. 연결 해시(다중집합)로 바꾸는 게 맞음.
- 이미지의 [계획] 표시로 구현 여부를 판단하지 말라는 것: 이미지 작성 시점이 이전이라 LR/RF/드리프트/CT/교체가
  [계획]으로 돼 있지만 현재 코드에는 구현돼 있음. 7단계 그림의 "분류: F1·Recall·오탐률"도 CN7은 현재 검사 예산(found_TP) 기준이라
  문서·그림 갱신 필요.

[시작 전에 정할 것 3가지]
1) 단계 진행(1차 P0부터) vs 한 번에 전체
2) pipeline_runtime.py 최소 수정 허용 + 감사는 보관본 방식
3) 제품 ID 계약 기본값(데이터셋 내 전역 고유) 수용 여부
