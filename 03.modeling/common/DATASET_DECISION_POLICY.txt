제품 ID 계약 (2026-10-05 결정: A 기본 + C 예외)
- A(기본 규칙): record_id 또는 product_id가 있으면 생산 제품 ID로 본다. 해당 데이터셋(cn7/rg3) 안에서 전역 고유하고
  원천 시스템(MES 쇼트 카운터·시리얼 등)이 발급한 값이어야 한다. 중복 판단과 제품-입력-라벨 연결의 1차 근거.
- batch_id는 전송 이벤트 ID다. 제품 ID가 아니다.
- C(예외 경로): 제품 ID가 없으면 내부 '<batch_id>:<행번호>'를 쓰되 배치 간 비교에 쓰지 않는다.
  중복은 내용이 같을 때 '중복 의심 보류'로만 판단한다. 'Unnamed: 0'은 파일 행 번호이며 ID가 아니다.
- 현재 대회 자료(moldset_*.csv)에는 생산 ID·생산 시각이 없어 전부 C 경로다. 따라서 재전송과
  '같은 설정의 새 생산'을 완벽히 구분하는 것은 실제 제품 ID가 들어오는 현장에서만 보장된다.
- processing.json·예약·수집 manifest에 id_mode(explicit_product_id / no_product_id_compat)를 기록한다.
- A 경로 ID 검증(2026-10-05 보완): ID 열이 있으면 모든 값이 문자열 또는 정수여야 하고 결측·빈 값·앞뒤 공백·실수형을 허용하지 않는다.
  위반이면 예약 전에 held(사유 명시)로 거부한다. ID 열이 있다는 이유만으로 유효한 생산 ID로 인정하지 않는다.
  생산 ID가 없는 자료는 ID 열 없이 보내 C 경로로 처리한다.

배치 중복 차단 (CN7·RG3 공통)
- 1차 근거는 명시 제품 ID(record_id·product_id). 이전 배치와 겹치면 held.
- 제품 ID가 없으면 내용으로만 판단: 이전 배치와 내용이 같으면 '중복 의심'으로 held.
- 제품 ID가 모두 새롭고 내용만 같으면 별도 생산 건으로 수집하고 duplicate_note에 기록한다
  (같은 조건에서 실제로 새로 생산된 제품의 빈도를 지우지 않기 위해).
- 내용 키는 패턴 요약(fingerprint별 제품 수·정상 수·불량 수·대표 라벨)의 해시다.
  행 순서만 바뀐 재전송도 같은 내용으로 판단한다(2026-10-05, 이전에는 행 순서에 따라 해시가 달라졌음).
- 같은 로트 재전송이 두 개의 감지 윈도로 집계되어 지속 변화(review)·CT를 여는 문제를 막는다.
- 상태 저장: runtime/<dataset>/dedup_index.json. 이 기능 도입 전 배치는 색인되지 않는다.
- 제품 ID가 없는 배치는 내용 해시로만 판단하므로, 운영 배치에는 제품 ID 제공을 권장한다.
- 제품 ID 비교는 record_id·product_id 열만 사용한다. 'Unnamed: 0'은 파일별 행 번호(0..n-1)일 수 있어 배치 간 비교에서 제외한다.

배치 처리 단계와 재시도 (2026-10-05)
- 수집(ingest)은 세 단계로 나눠 batches/<ID>/processing.json에 기록한다.
  수집 확정(파일·장부·중복 색인 등록) → 분포 감지(drift) → 검사 안내(CN7 우선순위 / RG3 불확실 단계)
  stage: drift_pending → advice_pending → completed, 실패 시 drift_failed / advice_failed(+error)
- 감지·안내가 실패해도 수집은 유지된다. 같은 batch_id로 다시 보내거나 resume 명령으로 못 끝낸 단계만 다시 실행한다.
  다시 저장하거나 장부에 두 번 넣지 않는다. 다른 batch_id로 다시 보내면 중복으로 held.
- 같은 batch_id에 다른 내용이 오면 status=conflict로 거부하고 기존 배치는 건드리지 않는다.
- held 배치(좌표 미확인 등)는 저장된 것이 없으므로 같은 batch_id로 다시 보낼 수 있다(이전 시도는 held_archive에 보관).
- 이미 끝난 배치를 다시 보내면 already_completed로 알려주고 아무것도 바꾸지 않는다.
- 수집 확정 도중 실패 대비(2026-10-05 2차): 파일 저장 '전에' 중복 색인에 예약(reservations)을 먼저 기록한다.
  저장·장부·처리 상태 기록 중 어디서 멈춰도 같은 내용·제품 ID는 다른 batch_id로 들어오지 못하고(held),
  pending 목록에 commit_incomplete(파일 저장됨) 또는 reserved_not_stored(저장 전 중단)로 표시된다.
  같은 batch_id로 다시 보내거나 resume하면 장부·처리 상태를 마저 기록하고 감지·안내까지 끝낸다. 끝나면 예약은 지운다.
  예약 기록 자체가 실패하면 아무것도 저장되지 않는다. 기본 수집이 held로 끝나면 예약을 되돌린다.
  예약이 남은 batch_id로 다른 내용이나 다른 제품 ID가 오면 conflict로 거부하고 기존 예약을 유지한다(2026-10-05 3차).
  이전 파일을 같은 batch_id로 다시 보내 마무리하거나, 새 자료는 새 batch_id로 보낸다.
- 재전송 비교 기준(2026-10-05 R02): 내용 해시와 별도로 '제품 ID-입력 지문-라벨' 연결 해시(link_sha256)를 최초 수집 때 고정하고
  예약·확정 미완료·후속 실패·완료 모든 단계의 재전송에서 비교한다.
  행 순서만 다름 → 같은 재전송(재개 또는 already_completed). 제품 ID 교체, ID별 입력·라벨 맞바꿈, 라벨 변경 → conflict, 원본 유지.
  라벨 정정은 재전송으로 처리하지 않는다(별도 정정 절차 필요, 현재 미구현: 정정 사유·출처·승인·이전 값 이력을 남기는 별도 명령).
  제품 ID가 없는 배치(C 경로)는 연결 해시가 없어 내용 해시로만 비교한다.
  수집이 끝난 배치는 processing.json의 기록을 믿지 않고, 해시 검증한 저장 products.csv에서 연결 해시를 다시 계산해 비교한다
  (연결 해시 도입 전 배치 포함). 저장 제품 파일이 없거나·읽을 수 없거나·바뀌었으면 비교 근거 부족으로 rejected.
  A/C 판단은 수집 당시 기록(id_mode)을 따르며 저장된 ID 모양으로 추정하지 않는다. 'Unnamed: 0' 행 번호만 있는 자료는 C 경로이므로
  같은 자료(행 번호가 바뀌거나 빠져도 내용이 같으면)는 already_completed. 처리 상태에 id_mode가 없으면 수집 manifest를 확인한다.
  둘 다 없는 실제 이전 기록은 저장 제품 ID 전부가 해당 배치로 색인에 등록돼 있어야 A로 확인한다.
  색인 누락·부분 누락·손상 또는 이전 C 자료의 계약 근거 부족은 rejected다. 미등록을 C로 추정하지 않는다.
  이전 C 자료는 원천 계약 확인 후 별도 이관이 필요하며 자동으로 과거 manifest를 수정하지 않는다.
  완료/확정 이력이 있는데 manifest가 누락·손상된 경우 rejected로 보존하고 재수집하지 않는다.
- 이미 수집된 batch_id로 재전송했는데 자료를 검증할 수 없으면(좌표 미확인·입력 오류) 성공으로 답하지 않고 rejected로 거부한다.
  미완료 단계 재개는 resume 명령(자료 없이)으로 한다.
- 미완료 배치 확인: pipeline_cli.py --dataset <cn7|rg3> pending

CN7 — 기본 판정: 랜덤 포레스트 + 검사 예산(cn7_decision_mode='budget')
- 운영 모델 종류 cn7_model_kind 기본 'rf'. accepted 배치마다 위험 점수 순위를 매겨
  상위 inspection_fraction(기본 10%) 제품을 검사 대상으로 표시: inspection_priority.json/csv/txt.
  경계 동점 규칙 cn7_tie_rule(기본 exact_k): 정확히 예산 수(k)만 표시한다.
  선택 순서(실행·평가 공통): 점수 높은 순 → 입력 패턴 지문(fingerprint) 문자열 순 → record_id 순. 라벨은 쓰지 않는다.
  평가의 판정 지표 found_TP는 이 순서로 실제 고른 패턴의 위험 수다(2026-10-05 2차: 이전엔 무작위 동점 기대값을 써서 실행과 달랐음).
  무작위로 동점을 고를 때의 값은 random_tie_expected_TP/min/max로 참고만 기록한다.
  all_ties를 고르면 동점을 모두 표시하고 예산 초과 수(over_budget)를 기록하며, 평가도 동점 전부로 계산한다.
  검사 비율은 0 초과 1 이하만 허용한다(0%는 거부, 배치당 최소 1개 검사).
  모델 선정(select-cn7)·승격 판단은 exact_k에서만 가능하다(2026-10-05 R03). all_ties로 선정하면 거부, 평가하면 미통과(참고 전용),
  all_ties 평가 기록으로는 승격할 수 없다. 이유: all_ties는 후보마다 실제 검사 수가 달라 동일 검사량 비교가 아니다.
  평가 기록에는 inspected(실제 검사 수)·over_budget를 함께 남기고, capture_of_reachable은 found_TP / min(실제 검사 수, 위험 수)로 계산한다.
  all_ties 배치 결과는 열람용으로 남긴다. 평가는 고유 패턴 단위의 위험 이력 발견 수이며 실제 제품 불량 발견률이 아니다.
  배치 예산은 제품 수 기준(unit=product), 평가 예산은 고유 패턴 수 기준(unit=unique_pattern)이다.
  RF 운영 모델이 없으면 status=no_active_model.
- 근거(개발 OOF만, Test 미사용, 위험 11개): 상위 10% 검사 시 위험 발견
  RF(운영 고정 설정) 9개·AUC 0.940 / LR(튜닝 설정) 8개·0.882 / OCSVM(선택 설정) 4개·0.798.
  재현: report_decision_examples.py → cn7_budget_comparison.json
- 평가·승격(budget 모드): 같은 평가 자료·같은 검사량에서 위험 발견 기대 수로 비교.
  예산 내 최대 발견 가능 수(min(k, 위험 수))의 min_budget_capture(기본 0.5) 이상이어야 하고,
  운영 모델이 있으면 그보다 많이 찾아야 한다. 고정 임계값 F1·recall·precision 조건은 이 모드에서 쓰지 않는다.
- 검사 비율과 최소 발견 비율은 Test를 보기 전에 현장 검사 여력에 맞춰 확정한다.
- --cn7-mode threshold로 이전 고정 임계값 정책(아래)을 쓸 수 있다.

CN7 — threshold 모드(선택)
- LR·RF·OCSVM을 동일 평가 자료에서 비교하고 기준 통과 후보 중 F1, recall, FPR 순으로 선택.
- 기본 최소 recall 0.5, precision 0.2, 최대 FPR 0.2는 잠정 운영 정책이다.
  통계적으로 최적이거나 현장 승인된 수치가 아니며 평가 전에 검사 비용에 맞게 확정해야 한다.
- 선택 보고서에 검사 예산(상위 10%) 기준 탐지 수를 참고로 함께 기록한다.
  CN7은 순위는 맞는데 고정 임계값이 실패한 이력이 있으므로 두 관점을 함께 본다.
- 선정에 사용한 평가 자료로는 promote할 수 없다. 승격에는 별도 평가 자료가 필요하다.
- 기존 최소 평가 정상/위험 패턴 수, 독립 평가 목적, 학습 중복 금지 조건 유지.
- 기존 모델이 있으면 F1 개선·recall 유지도 충족해야 함.
- 모든 후보 미달, 표본 부족, 기존 Test 후속 평가이면 selected=null, selection_held.
- 초기 선택은 비교할 운영 모델이 없어도 가능하나 자동 활성화·배포하지 않음.

감지 결과와 소비 장부 (2026-10-05 R01)
- 감지는 drift/<ID>.json(결과)을 먼저 저장하고 monitor.json(소비 목록·이력)을 기록한다.
  두 기록 사이에서 멈추면, 다음 감지 시작 시 또는 resume 시 이력에 없는 감지 결과를 drift ID 기준으로 한 번만 반영한다.
  → 이미 감지에 쓴 배치를 다음 윈도에서 다시 소비하지 않고, 같은 drift를 이력에 두 번 넣지 않는다.
- 연속 초과(streak)는 바로 이전 확정 윈도의 기준선과 경보 정책이 같을 때만 이어진다. 정책/기준선 A→B→A 복귀도 1부터 다시 센다.
- continuity_version=2로 이전 계산 규칙의 횟수를 이어 쓰지 않는다. 표본 부족 waiting은 확정 윈도로 세지 않는다.
- 수동 복구: pipeline_cli.py --dataset <cn7|rg3> reconcile-monitor
- 이 수정은 pipeline_runtime.py의 Operations 클래스에 들어갔다. 학습 경로 정의는 바꾸지 않았고,
  LR 감사는 03.modeling/common/provenance의 보관본으로 출처를 확인한다(provenance/README.txt).

감지 경보선 캐시 (2026-10-05)
- 경보선 계산 결과(baselines/<ID>/calibration_*.json)에 분위수·반복 수·기준선 ID·pipeline_runtime 코드 해시를 기록한다.
- 정책(예: drift_quantile 0.99 → 0.95)이나 코드가 바뀌면 이전 캐시를 calibration_archive로 옮기고 다시 계산한다.
- 드리프트 결과(drift/<ID>.json)에도 calibration_signature로 사용한 정책을 남긴다.

평가 용도 기록 (2026-10-05)
- register_evaluation 시 manifest.json(용도 purpose·패턴 목록·CSV 해시)의 해시를 manifest_integrity.json에 고정한다.
- evaluate·promote에서 다시 대조한다. 등록 후 용도가 바뀌면 평가·승격을 거부한다.
- 이 기능 도입 전에 등록한 평가 자료는 다시 등록해야 평가할 수 있다.

현재 데이터의 한계
CN7 기존 Test 위험은 3개로 최소 평가 위험 5개에 미달한다. 이미 관찰한 후속 평가 자료이기도 하다.
따라서 현재 소스로 운영 가능한 CN7 모델을 선정 완료했다고 말하지 않는다.
RG3 예시는 기존 Test 패턴에 개발 참조를 적용한 출력 예시이며 새 현장 배치 검증이 아니다.
