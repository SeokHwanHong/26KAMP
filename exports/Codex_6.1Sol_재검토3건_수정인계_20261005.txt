1. 검사 실행기 실패 판정
run_checks_only.py는 회귀 subprocess 종료 코드만 최종 코드에 반영한다.
baseline_status valid=false나 상태 조회 예외가 있어도 passed=true/exit_code=0이 된다.
실제 20261005T213706 실행에서 CN7 기준선은 valid=true, RG3는 기준선 포인터 없음으로 valid=false였지만 전체 종료 코드 0이었다.
회귀 테스트 통과와 운영 준비 상태를 별도로 기록하고 기준선 오류·상태 조회 실패를 최종 실패 코드에 반영해.
미완료 배치의 처리 정책은 정상 대기와 오류를 구분해 명시하고, 모든 pending을 무조건 실패로 간주하지 마.
기준선을 자동 생성하거나 RG3 운영 상태를 임의로 고치지 마. 초기 미준비인지 유실인지 현재 자료만으로 단정하지 마.
mock 상태(valid/invalid/exception)와 회귀 성공/실패 조합으로 테스트해.
수정 후 실제 RG3 기준선 부재 때문에 checks-only가 비정상 종료하는 것은 기대 동작이다.
이를 회귀 테스트 자체의 실패와 구분하여 보고해.

2. 완료 배치 resume 저장 자료 검증
decision_runtime.Operations.resume은 _retry(batch_id,None)을 호출한다.
_retry의 저장 products.csv 검증은 key가 있을 때만 실행되므로 완료 배치 products.csv를 삭제해도
resume이 accepted/already_completed를 반환한다. 임시 RG3 배치에서 재현했다.
완료 응답 전에 저장 자료의 무결성을 검증하고, 검증 불가이면 명시적 rejected/오류를 반환해.
원본 재전송과 resume은 입력 유무가 다르므로 기존 _stored_link 로직을 기계적으로 적용하지 말고 필요한 계약을 검토해.
누락·디렉터리·읽기 실패·해시 변경·manifest 손상과 정상 완료의 조합을 검사해.
중복 수집, 장부 재소비, 기존 R01/R02 복구, A/C ID 계약 보호를 유지해.

3. advice_context 영속 기록
workflow_runtime._advise가 새로 읽은 processing.json에 advice_context를 저장하지만,
decision_runtime._finish가 이전 proc 전체를 저장해 이 키를 지운다.
합성 배치 정상 완료 후 키가 없는 것을 확인했다.
별도 advice_history/<revision>/context.json에는 출처가 남으므로 전체 출처 소실로 과장하지 마.
완료·실패 처리의 최신 상태 병합 또는 단일 저장 책임으로 고쳐.
정상 완료, advice 실패 후 재개, 모델 교체 후 재개, waiting 후속 안내 갱신에서
최초 context/후속 revision의 모델·기준선·정책 연결과 원래 오류/단계 정보 보존을 검증해.
