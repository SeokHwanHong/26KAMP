================ 복사할 프롬프트 시작 ================

현재 KAMP 프로젝트를 첨부한 7단계 아키텍처의 방향으로 완성해줘.
팀장님의 추가 검토 PDF를 현재 코드와 대조하고, 아래 범위의 구현·회귀 테스트·격리 종단 리허설까지 수행해.
기존 수정에서 통과한 기능을 보존하면서 단계 간 데이터·상태·버전·복구 규칙을 보완하는 작업이야.
모델 종류 추가, 성능 튜닝, 전체 재작성, 화면·DB·클라우드 구축은 이번 범위가 아니야.

0. 확인 자료와 작업 원칙
- README, common의 설계·운영 문서, decision_runtime.py, pipeline_runtime.py, pipeline_cli.py,
  04_operations.ipynb, tests, run_20261005_checks_and_rf.py 및 최근 테스트 로그를 먼저 읽어.
- 첨부 PDF의 재현된 결함과 정적 검토 의견을 구분해. 이미지의 [계획] 표시는 작성 당시 상태이지,
  현재 코드를 미구현이라고 단정하는 근거가 아니야. 최신 코드로 구현 상태를 판정해.
- 다른 작업자의 변경, 원본 데이터, 고정 개발/Test 분할, 과거 결과를 보존해.
- 실제 runtime의 모델·레지스트리·기준선은 변경하지 마. 운영 전환 실험은 별도 state-root에서 해.
- 전체 검사 후 RF를 실제 등록하는 기존 실행기를 검수 목적으로 무심코 실행하지 마.
- 실제 파이썬 코드로 검증하고 실행하지 않은 결과를 통과했다고 보고하지 마.
- 기존 감사 해시를 맞추려고 과거 기록을 수정하거나 해시 검증을 삭제하지 마.
  하위 런타임 변경이 꼭 필요하면 최소 범위로 변경하고, 과거 소스/결과의 출처 보존과
  새 코드의 버전 검증을 분리해. 해시 때문에 불완전한 우회 계층을 계속 쌓지는 마.

1. 유지할 7단계 아키텍처
1) 데이터 준비: CN7/RG3 분리, 24개 입력, 라벨 유무·스키마·스케일 정합 확인, 제품/배치 ID 보존.
2) EDA·전처리: 원본 제품 기록과 빈도를 보존하고 동일 입력 패턴만 집계. 라벨 포함은 max(label),
   비라벨은 라벨 생성 없이 별도 보관. 초기·배치의 처리 의미와 원본 연결이 일치해야 해.
3) 초기 모델·기준선: IF/OCSVM 정상 기준 학습, LR/RF 정상·위험 학습. 모델별 독립 버전 관리.
   이미지 IF→OCSVM 화살표만으로 점수 직렬 연결이나 pseudo-labeling을 새로 도입하지 마.
4) 배치 유입·추론: 저장된 전처리·모델 재사용. 추론 시 scaler 재적합 금지.
   입력·라벨 상태·점수·예측·모델 버전·원본 ID를 연결해 저장.
5) 드리프트: 기준선 대비 입력/조합/모델 출력 분포 변화, 크기·지속성·표본 조건 판단.
   waiting은 판단 대기, normal은 분포 경보 없음, watch는 관찰, review는 원인 검토야.
   이 상태를 개별 제품의 정상·불량 확정으로 번역하지 마.
6) 모델별 CT: 변화 근거·원인 확인·확정 라벨·고유 패턴 수가 충분할 때 후보를 전체 재학습.
   IF/OCSVM은 확인된 정상 패턴, LR/RF는 정상·위험 패턴을 사용해.
   비라벨·예측 라벨로 CT하지 않고, 공정 이상을 자동으로 새 정상에 편입하지 마.
7) 검증·교체: 동일하고 분리된 평가 자료로 비교하고 통과한 해당 모델만 명시적으로 교체.
   미달·표본 부족이면 기존 모델 유지. 이전 버전과 롤백 기록 보존.

CN7 검사 예산 순위와 RG3 정보 부족·추가 검사 안내는 이 공통 흐름의 데이터별 결과 정책이야.
CN7 RF 초기 운영 등록을 세 모델 중 최적 모델로 검증 완료한 것으로 표현하지 마.
RG3는 위험 이력과 분포 변화의 근거를 보여주되 확정 불량 확률로 표현하지 마.
TV·Wilson의 계산법과 24개 공정 입력을 이번 문제 해결 명목으로 변경하지 마.
생산 시간순은 미확인이다. 배치 도착 순서의 연속 경보를 실제 생산 시계열 검증처럼 표현하지 마.

2. 가장 먼저: R01 감지 결과와 소비 원장의 장애 복구
현재 재현: M1의 drift JSON을 기록한 뒤 monitor.json 저장을 실패시키면 drift_failed가 된다.
resume는 남은 drift를 찾아 completed로 만들지만 consumed/history를 복구하지 않는다.
그 다음 M2 감지의 batch_ids가 [M1,M2]가 되어 이미 감지한 M1이 다시 집계된다.
Codex도 현재 코드에서 이 결과를 재현했다.

요구사항:
- 감지 결과와 consumed/history를 함께 확정하는 규칙을 정해 구현해.
- 파일 기반을 유지해도 된다. 여러 파일을 저장하는 중 어디서 중단돼도 복구 가능한 기록을 둬.
- drift_id를 기준으로 소비 원장 반영을 한 번만 복구하고, 같은 drift/history를 중복 추가하지 마.
- 복구 후 다음 윈도는 이미 확정된 배치를 다시 소비하지 않아야 해.
- streak는 확정된 비중복 윈도와 같은 기준선·정책에 대해서만 이어가야 해.
- 감지 JSON 직후, monitor 직전/직후, 처리 상태 기록 직전/직후 실패를 주입해 검증해.
- resume를 여러 번 호출해도 소비 목록·history·streak·검사 안내가 불필요하게 증가하지 않아야 해.

3. R02: 완료된 배치까지 최초 제품 연결을 보호
현재 재현: 완료된 M1의 입력·라벨은 그대로 두고 제품 ID만 바꾸어 같은 M1로 보내면
accepted/already_completed가 반환되며 기존 제품 기록만 남는다. Codex도 재현했다.
예약 중인 배치만 보호하는 현재 검증을 모든 재시도로 확장해.

요구사항:
- 관측 내용 요약 해시와 별도로, 정규화된 제품 ID-24개 입력-라벨 상태/값의 연결 해시를 보존해.
- ID 집합만 비교하지 마. 같은 ID 집합에서 제품별 입력이나 라벨을 맞바꾼 경우도 탐지해야 해.
- 동일 행 다중집합의 재정렬은 같은 재전송으로 인정하되 중복 행의 발생 횟수도 보존해.
- reserved/commit_incomplete/후속 처리 실패/completed 전 단계에서 같은 규칙을 적용해.
- 입력 검증 실패로 key=None이 되었다고 내용 일치 확인을 건너뛰고 성공 응답하지 마.
- 동일 자료만 재개 또는 already_completed. ID·연결·라벨 변경은 conflict로 거부하고 원본 유지.
- ID의 발급 주체·고유 범위·데이터셋/lot 범위를 명시해. 현재 파일 내부 임시 행 번호를
  전역 제품 ID처럼 취급하지 마. 생산 ID 미확보 자료는 기존 호환 경로와 한계를 분리해.
- 같은 입력의 새 제품은 제품 관측으로 수집하고 학습 패턴만 통합해. 동일 조건 생산을 삭제하지 마.
- 라벨 사후 도착·정정은 재전송과 구분해. 이번에는 기존 라벨을 조용히 덮어쓰지 않도록
  명시적 거부/안내 및 향후 정정 인터페이스의 요구사항을 문서화해. 임의 정답 생성은 하지 마.

4. R03: 선택·승격에서 실제 검사 예산 일치
현재 all_ties 재현: 10패턴, 위험5, 동일점수, 검사10%에서 k=1, flagged=10, found_TP=5,
capture_of_reachable=5.0이다. Codex도 계산을 재현했다.

이번 구현 결정:
- 후보 선정·승격 판단은 exact_k로 제한해. all_ties 평가로 승격 근거를 만들지 마.
- all_ties를 결과 열람용으로 유지한다면 실제 검사 수·초과 검사 수와 참고 전용 표시를 해.
  잘못된 요청을 자동으로 exact_k로 바꾸기보다 명시적으로 거부하거나 별도 모드로 분리해.
- 운영·평가의 exact_k 선택 함수와 라벨 미사용 동점 규칙을 유지해.
- found_TP는 실제 선택한 위험 이력 패턴 수, random_tie_*는 참고값으로 분리해.
- capture 지표를 숫자만 1로 자르는 방식으로 문제를 숨기지 마. 분모와 실제 검사 수를 맞춰.
- 운영 예산은 제품 수, 현재 평가 예산은 고유 패턴 수라는 차이를 결과에 명시해.
  같은 선택 규칙이 실제 제품 불량 발견률까지 검증했다는 뜻은 아니야.
- 후속 실제 제품 검사 성과는 실제 제품 정답을 확보했을 때 별도 평가해.

5. 안내·추론·감지 버전과 waiting 후속 연결
다음은 보고서의 정적 검토 의견이다. 먼저 현 코드에서 재현한 뒤 필요한 부분을 보완해.
- 배치 추론 당시 모델, 감지 당시 기준선·모델·정책, 안내 버전을 각각 명확히 기록해.
- advice_failed 후 운영 모델이 바뀌어도 재개가 현재 active 모델을 몰래 사용하지 않도록 해.
  기본 방침은 최초 기록에 고정된 버전을 재사용하는 것. 원래 버전이 없으면 실패를 명시해.
- 새 버전으로 재산출하는 기능이 있다면 별도 revision을 생성하고 점수·순위·근거를 함께 갱신해.
- completed는 요청 처리 완료, waiting은 분포 판단 미완료일 수 있다. 두 상태를 별도 필드로 표시해.
- 나중 윈도에 이전 waiting 배치가 포함되면 batch→drift 연결을 갱신하고 최신 판단을 조회할 수 있게 해.
  과거 당시 안내는 이력으로 보존하고 현재 안내와 구분해. 최신화 때문에 데이터를 재수집하지 마.
- RG3는 불확실 정도, 분포 변화, 검사 권고를 분리해. 범위 내·경보 없음도 품질 정상 보증은 아니야.

6. 동시 명령·기준선·모델 전환 복구
- ingest, standalone detect, promote, rollback의 잠금 범위·획득 순서를 통일해.
  현재 규모에서는 명확한 직렬화가 적절해. 서로 다른 잠금의 역순 획득으로 교착을 만들지 마.
- 서로 다른 경보 정책의 동시 detect가 캐시 파일에 잘못된 서명을 붙이지 않도록 해.
- 입력 참조 자료·구간은 기본적으로 기존 기준을 유지하고 모델 교체 시 모델 출력 기준선을 재생성해.
  신규 배치를 자동으로 정상 참조에 흡수하지 마. 참조 교체는 별도 명시적 정책이야.
- 모델 레지스트리 변경 후 기준선 생성 실패가 발생해도 어느 버전이 유효한지 추적·재개 가능해야 해.
  새 기준선 준비 후 묶음 전환 또는 명시적 전환 기록/복구 등 검증 가능한 방식을 선택해.
- 롤백 실패도 동일한 수준으로 기록·복구해. 모델과 기준선이 불일치한 상태의 추론을 막아.
- baseline의 참조 파일·정의·모델·정책 버전을 검증하고 같은 자료·같은 정책의 재현성을 확인해.

7. 평가 자료의 정합성과 재등록 이력
- CSV 입력값에서 fingerprint를 다시 계산해 저장 열·manifest 패턴 목록과 대조해.
- 평가 목적, 라벨 출처, 데이터셋, 내용 및 학습/평가 역할을 함께 고정해.
- 같은 평가 자료를 새 ID로 등록했다고 독립성이 생기지 않아. 정규화 내용·패턴 집합과
  원본/이전 평가 ID·선정 사용 이력을 연결해 재등록으로 승격 금지를 우회하지 못하게 해.
- 완전 동일 자료뿐 아니라 선정 자료와 겹치는 패턴도 별도 최종 평가의 근거로 섞이지 않게 해.
- 기존 Test는 historical_followup으로 유지하고 위험 표본 수 최소 조건을 낮추지 마.
- 기존 검증은 과거 자료를 학습에 사용하지 않았다는 증거와 분리해. 해시는 악의적 변조를
  완전히 막는 인증 장치가 아니라 기록 불일치 탐지 수단이라는 범위로 설명해.

8. 실행기·학습 연결·문서
- 검사 실패나 RF/기준선 준비 실패는 프로세스의 비정상 종료 코드로 전달해.
- RF가 이미 active여도 baseline의 유효성을 확인해야 해. 테스트가 자동 운영 등록으로 이어지지 않게 분리해.
- RF 고정 초기 기준과 별도 탐색 결과를 구분하고, 탐색 결과의 운영 등록이 필요하면 기존
  모델 계약·전처리·선택 근거·해시를 검증하는 명시적 연결로 해. 새 튜닝은 하지 마.
- 이미지 1~7단계별 실제 진입점·입출력·상태·보류·실패·재개 명령을 문서화해.
- IF/OCSVM/LR/RF의 현재 구현·연결·인수 검증 완료를 구분해. 이미지의 계획 문구만으로 코드를 되돌리지 마.
- 초기와 배치의 전처리 정책은 유지하고 제품 행/패턴 행/원본 연결/횟수가 일치하는지 검증해.
- CT는 기존/신규 패턴과 역할을 추적하고, 비라벨·평가 전용 자료가 들어가지 않게 해.

9. 필수 테스트 및 완료 기준
먼저 R01~R03을 재현한 뒤 수정해. 이후 위 정적 검토 항목의 실제 실패 조건을 확인하고 회귀 테스트를 추가해.
최소 아래 시나리오를 포함해:
A. drift 저장→monitor 실패→resume→다음 배치: 기존 배치 재소비 없음, history 중복 없음.
B. 수집 예약/CSV/manifest/ledger/processing/index 각 쓰기 실패 후 동일 자료 재개.
C. 미완료·완료 배치 재전송: 재정렬 허용, ID 교체·ID별 입력/라벨 교환·잘못된 입력 거부.
D. 같은 입력의 새 생산 보존, 동일 제품 재전송만 차단, 원본 제품 수·패턴 집계 일치.
E. exact_k의 동점·비동점·작은 배치·0% 거부, all_ties 선택/승격 차단, 제품/패턴 단위 표기.
F. waiting 배치가 후속 review 윈도에 포함될 때 최신 안내 연결, 과거 안내 보존.
G. 안내 실패 후 모델 전환/재개, 동시 ingest·detect·교체의 버전 일관성 및 잠금 복구.
H. 평가 목적 변경, CSV 지문·목록 불일치, 선정 자료의 재등록/겹침, 과거 Test 사용 차단.
I. 승격/롤백 기준선 생성 실패 후 복구, 실행기 실패 종료 코드.
J. CN7/RG3 각각 격리 state-root에서 초기 기준→배치→드리프트→원인/라벨 확인→CT 후보→
   평가→유지/승격→롤백까지 연결. 통과용/미달용 합성 fixture로 기능을 검증해.

전체 검사와 기존 LR 저장 결과 재검산도 실행해. 새 변경과 관련 없는 대규모 학습은 반복하지 마.
테스트 수는 실행 결과에서 집계하고 실패/미실행/환경 불일치를 숨기지 마.
기존 결과를 덮어쓰지 말고 새 run_id, 의존성 버전, 코드/자료 해시를 남겨.
실제 runtime 실행 전후 해시가 같은지 확인해. 운영 모델을 바꿔 통과 사례를 만들지 마.
합성 종단 통과는 흐름 검증이고, 현장 정확도나 최종 최적 모델 입증이 아니야.

10. 최종 제출
- 요청 항목별 수정 위치, 변경 전/후, 재현 결과, 회귀 테스트 결과 표
- R01~R03 해결 근거와 그 외 정적 검토 항목의 구현/검증/보류 구분
- 7단계 아키텍처와 실제 코드 연결, 기존 전처리 유지 여부
- 실패·재시작·중복·버전 전환의 상태 흐름과 실행 명령
- 제품/패턴 단위, CN7 검사 예산, RG3 안내의 통계적 의미와 한계
- 실제 테스트 로그와 요약, 환경·해시·runtime 불변 결과
- 추가로 확인이 필요한 현장 조건과 남은 결함을 명확히 기록

보고서에 언급됐다는 이유만으로 전부 해결됐다고 표기하지 말고, 구현과 실제 실행 근거로 완료를 판단해줘.
